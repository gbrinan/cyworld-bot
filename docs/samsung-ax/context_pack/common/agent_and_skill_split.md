# 에이전트와 스킬로 나누기 — 분해표를 도구로 옮기는 법

> `task_decomposition.md`에서 ①프로세스 ②IPO ③꼬리표 ④묶기까지 했습니다. 여기서 ⑤⑥을 합니다.
> **묶음 하나를 만들 때, 무엇을 에이전트에 두고 무엇을 스킬로 뗄 것인가**가 이 문서의 질문입니다.

---

## 1. 두 그릇의 차이

| | **에이전트** | **스킬** |
|---|---|---|
| 무엇인가 | 일하는 자리. 계속 살아 있음 | 절차 묶음. 필요할 때 꺼내 읽힘 |
| 담는 것 | 이름 · 지침 · **참조 파일** · 대화 시작 예시 · (ChatGPT) 예약 | `SKILL.md` — name · description · 본문(절차·양식·금지·검수) + 부속 파일 |
| 누구 것인가 | **이 사람 / 이 팀** | **누가 써도 같음.** 조직 디렉터리에 공유 |
| 바뀌는 빈도 | 자주 (담당·데이터가 바뀌면) | 드물게 (일하는 방식이 바뀔 때만) |
| 어디서 만드나 | ChatGPT `에이전트` · Gemini Enterprise `에이전트` | 에이전트 편집 화면의 `스킬 추가` |

**에이전트는 그릇, 스킬은 내용물이 아닙니다.** 둘 다 내용을 담습니다. 나누는 기준은 **누가 써도 같은가**입니다.

---

## 2. 나누는 기준 — 세 가지 질문

묶음의 각 줄에 대해 묻습니다.

```
1. 다른 사람이 해도 똑같이 하는가        → 예: 스킬
2. 다른 업무에서도 쓰는가                → 예: 스킬
3. 내 팀·내 데이터·내 담당에만 맞는가     → 예: 에이전트
```

| 스킬로 떼는 것 | 에이전트에 두는 것 |
|---|---|
| 작업 순서 (④ 처리 순서) | 참조 파일 (우리 팀 실적·카탈로그·고객 목록) |
| 출력 양식 (⑤ 출력 형식) | 우리 팀이 쓰는 용어·분류 명칭 |
| 금지 사항 (⑥ 중단·보안) | 대화 시작 예시 |
| 검수 기준 (⑦ 성공 기준) | 실행 주기 (예약) |
| 입출력 예시 (정답 1건) | 담당 수요처·권역 |

**"매번 달라지는 것은 지침에 넣지 않는다"** 를 도구로 옮기면 이 표가 됩니다.
지침에 담당 수요처 이름을 박아 두면, 담당이 바뀔 때마다 지침을 고쳐야 합니다. 참조 파일로 두면 파일만 바꿉니다.

---

## 3. 이 과정의 3층과 같은 구조입니다

우리가 `context_pack/`을 세 층으로 나눈 것과 정확히 같습니다.

```
common/          방법론 · 절차 · 양식      →   스킬
modules/*/01_data/   팀별 데이터           →   에이전트의 참조 파일
modules/*/02_prompt/ 완성 지시문           →   스킬 본문 + 에이전트 지침
```

**팀이 바뀌면 스킬은 그대로 두고 참조 파일만 바꿉니다.** 9차수를 운영해도 스킬은 하나입니다.

---

## 4. 해 보기 — D 모듈

묶음: 2~8번 (데이터 점검 → 버티컬 분석 → TOP 3 → 근거)

### 스킬로 뗀 것 — `recommending-products-by-vertical`

```
name        : recommending-products-by-vertical
description : 과거 B2B 판매 실적에서 대상 수요처와 같은 버티컬의 구매 패턴을 분석해
              근거가 붙은 추천 제품 3개를 HTML 보고서로 만든다. 판매실적 파일과
              대상 수요처 정보를 받았을 때 사용한다.
본문
  1. 역할·목표      근거가 붙은 추천 초안을 만든다. 수치는 반드시 재계산한다
  2. 출력 형식      0.점검 / 1.대상 분석 / 2.버티컬 Insight / 3.TOP3 / 4.제안 Point
  3. 금지 사항      없는 값 채우지 않기 · 공급가를 제안가로 쓰지 않기 · 확정 견적 금지
  4. 검토 기준      점검이 먼저 나오는가 · 추천마다 근거 행 번호가 있는가
  5. 작업 단계      ④ 처리 순서 0~5 + 입출력 예시 1건
```

**5번 입출력 예시에는 `04_answer/recommend_D.html`이 들어갑니다.** 모듈의 정답 파일이 그대로 스킬의 예시가 됩니다.

### 에이전트에 둔 것

```
이름          : 버티컬 추천 도우미 (B2B팀)
지침          : "이 일은 recommending-products-by-vertical 스킬을 따른다."
                + 우리 팀 버티컬 명칭 · 우리 팀이 쓰는 용어
참조 파일      : sales_history.csv (우리 팀 실적)
대화 시작 예시  : 3개
```

**실적 파일이 매달 바뀌어도 스킬은 그대로입니다.** 유통전략팀이 같은 스킬에 자기 실적 파일을 붙이면 그 팀의 에이전트가 됩니다.

## 5. 해 보기 — A 모듈 (단계가 셋일 때도 에이전트는 하나)

A는 수집·프로파일·분석 셋을 하지만 **에이전트는 하나**입니다. 사이에 🔒이 없기 때문입니다. 스킬 본문의 작업 단계가 셋이 됩니다.

| 단계 | 스킬 본문으로 | 에이전트에 |
|---|---|---|
| 1 정기 수집 | 수집·중복 제거·4열 정리 절차 | **검색어 목록** (담당이 바뀌면 이것만) · **실행 주기** |
| 2 프로파일 | 질문 항목과 순서 · "모르면 비워 둔다" 규칙 | 우리 팀 프로파일 양식 |
| 3 기회 분석 | 신호 해석 · **준공 마이너스 6개월 역산** · 시나리오 갈래 · 대시보드 양식 | 담당 수요처 목록 |

```
에이전트  A_시장고객분석 (직판)      ← 하나
  └ 스킬  sensing-listed-builder-signals
       작업 단계 1 수집 → 2 프로파일 → 3 분석
  └ 참조 파일  target_builders.csv · rss_sources.md
  └ 실행 주기  주 1회
```

**단계 1이 스킬의 값어치를 가장 잘 보여줍니다.** 수집 절차는 매주 같고, 담당 수요처는 인사이동 때마다 바뀝니다.
절차를 스킬로 떼어 두면 후임자가 참조 파일만 바꿔 그대로 씁니다. **인수인계가 파일 한 개**가 됩니다.

## 6. ChatGPT와 Gemini에서 각각 어떻게 되나

| | ChatGPT | Gemini Enterprise |
|---|---|---|
| 에이전트 만들기 | 사이드바 `에이전트` → `만들기` | 사이드바 `에이전트` → `+ 새 에이전트` → **수동으로 빌드** |
| 지침 | `지침` 칸 | 지침 칸 |
| 참조 파일 | `파일 업로드` | 참조 파일 (리허설 C6 확인) |
| 스킬 | **`스킬 추가` 버튼** (9/11 캡처 확인) | 확인 필요 |
| 정기 실행 | **`예약`** (사이드바) | 확인 필요 |
| 조직 공유 | `Samsung Electronics - DX 디렉터리` | `Marketplace` |

**스킬 형식은 공개 표준입니다.** `SKILL.md` 한 장이 ChatGPT·Claude·Codex·Gemini CLI에서 같은 형식입니다.
그래서 도구가 바뀌어도 **스킬은 옮겨 갑니다.** 에이전트 화면만 다시 만들면 됩니다.

**스킬 기능이 막혀 있으면** 스킬 본문을 지침 칸에 그대로 붙여넣습니다. 나누는 연습은 그대로 하고 보관 장소만 달라집니다.
자세한 형식은 `skills_and_mcp.md` 2장.

## 7. ⑥ 실제로 만드는 순서

```
1. 스킬 본문을 먼저 씁니다        ← 절차·양식·금지·검수. 누가 써도 같은 것
2. 정답 1건을 만들어 5번에 붙입니다  ← 입출력 예시가 없으면 스킬이 안 먹습니다
3. 에이전트를 만들고 스킬을 연결합니다
4. 참조 파일을 올립니다            ← 내 팀 데이터
5. 대화 시작 예시 3개를 넣습니다
6. 테스트 3종을 돌립니다           ← 정상 · 경계 · 실패
7. 검수 5분 후 저장·공유합니다
```

**2번을 건너뛰지 않습니다.** 입출력 예시 없는 스킬은 "알아서 잘해줘"와 같습니다.
이 과정의 각 모듈이 `04_answer/`에 정답을 두는 이유가 이것입니다.

## 8. 자주 하는 실수

| 실수 | 왜 문제인가 | 고치는 법 |
|---|---|---|
| 담당 수요처 이름을 지침에 박음 | 담당이 바뀌면 지침을 고쳐야 함 | 참조 파일로 뺀다 |
| 스킬 하나에 업무 전체를 담음 | 🔒 지점을 AI가 지나침 | 🔒 앞에서 끊는다 (④) |
| 단계마다 에이전트를 따로 만듦 | 참조 파일을 세 곳에 올리고 셋을 따로 고침 | 🔒이 없으면 **한 에이전트의 단계**로 둔다 |
| description을 한 단어로 씀 | 언제 꺼내 쓸지 도구가 판단 못 함 | **무엇을 하고 언제 쓰는지** 3인칭으로 |
| 출력 예시 없이 양식만 씀 | 매번 다른 모양이 나옴 | 정답 1건을 붙인다 |
| 에이전트를 사람 수만큼 만듦 | 관리가 안 됨 | 스킬 하나 + 참조 파일 여러 벌 |
