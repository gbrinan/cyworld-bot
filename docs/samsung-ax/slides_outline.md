> **전제: 사내 환경은 웹 브라우저에서 포털을 통해 ChatGPT·Gemini를 불러 쓰는 방식입니다.**

## OPENING (4장)

### S01 — 표지
- 제목: **B2B 영업 AI Agent 실습**
- 부제: 시장·고객 분석 / 제안자료 작성 / 데이터 분석
- 하단: 삼성전자 | 2026

### S02 — 오늘 만드는 것
- 핵심 메시지: **세 개의 Agent가 하나의 영업 여정으로 이어집니다.**
- 본문: 체인 다이어그램
```
② Sensing  → customer_profile.md
③ Action   → proposal_draft.md
④ Analysis → report_draft.md
```
- 하단 한 줄: 각 단계의 결과를 파일로 저장해 다음 단계가 받습니다.
- 강사 노트: 여기서 "오늘 산출물은 세 개의 파일"이라고 못 박습니다.

### S03 — 오늘의 흐름
- 핵심 메시지: 6시간, 세 모듈, 같은 방법.
- 본문: 타임라인 (② 2h → ③ 2h → ④ 2h). ①⑤는 회색으로 표시하고 "삼성 자체 운영" 표기.
- 각 모듈 아래: 도입 15 / 실습1 20 / 실습2 35 / 실습3 25 / 시연 15 / 마무리 10

### S04 — 시작 전 준비
- 핵심 메시지: **탭 두 개를 엽니다 — AI 창과 메모장.**
- 본문 4항목
  1. 저장할 폴더를 만듭니다 (바탕화면/AX실습_내이름/)
  2. 작은 파일로 업로드 테스트 (`product_catalog.csv`, 1KB)
  3. 실행 횟수 예산 확인 (Deep Research 1회, 에이전트 3회)
  4. 실제 업무 파일은 올리지 않습니다 — 팩의 가상 데이터만
- 강사 노트: 4번은 반드시 소리 내어 읽습니다.

### S04b — 웹 환경에서 결과를 남기는 법 *(신규)*
- 핵심 메시지: **AI에게 파일을 만들어 달라고 하지 않습니다.**
- 본문: 4단계 그림
```
① 화면 출력을 드래그해 복사
② 메모장에 붙여넣기
③ customer_profile.md 로 저장
④ 다음 모듈에서 업로드
```
- 하단 박스: 업로드가 안 되면 → `paste/` 폴더의 표를 붙여넣습니다.
- 강사 노트: 이 장을 건너뛰면 모듈 마무리에서 절반이 인계 파일을 못 만듭니다. 반드시 시연합니다.

### S04c — 지시문은 메모장에 먼저 *(신규)*
- 핵심 메시지: 세션이 끊기면 채팅창의 지시문은 **사라집니다.**
- 본문: 좌우 비교
  - ✗ 채팅창에 바로 씀 → 새로고침하면 없어짐, 다음 차수에 다시 씀
  - ○ 메모장에 `agent02_prompt.md`로 저장 → 붙여넣어 사용, 고칠 때도 메모장에서
- 하단: 이게 "컨텍스트를 데이터로 다룬다"의 가장 작은 실천입니다.

## 공통 방법론 (9장) — 세 모듈 시작 전 한 번만

### S05 — 왜 Agent를 따로 만들지 않는가
- 핵심 메시지: **팀이 둘인데 Agent를 여섯 개 만들 수는 없습니다.**
- 본문: 좌우 비교
  - 왼쪽(✗): 팀마다 Agent 3개 = 6개, 차수마다 새로 제작
  - 오른쪽(○): 공통 Agent 3개 + 팀별 데이터 팩 2벌
- 하단: Agent는 "아는 것"이 아니라 **"받은 파일"**로 일합니다.

### S06 — 컨텍스트를 데이터로
- 핵심 메시지: 바뀌는 것과 안 바뀌는 것을 나눕니다.
- 본문: 2열 표

| 안 바뀜 (공통) | 바뀜 (팀별 팩) |
|---|---|
| 지시문 골격, 처리 순서, 출력 형식 | 업무 상황 |
| 검수 기준, 중단 규칙 | 입력 데이터와 컬럼 |
| 테스트 구성 | 고객·제품 정보 |
| 사람 승인 지점 | 결과물 서식 |

- 강사 노트: "지시문에 고객사 이름을 적지 않고, 고객사 파일을 올립니다."

### S07 — 일반 대화와 업무 Agent
- 핵심 메시지: 한 번 쓰고 버리는 것과, 반복해서 같은 기준으로 도는 것은 다릅니다.
- 본문: 2열 비교 (대화: 맥락을 매번 전달 / 품질 변동 / 1회성 · Agent: 역할·지식·출력 고정 / 예외에서 중단 / 반복 업무)
- 하단: 반복 빈도와 오류 비용이 높을수록 Agent 설계가 필요합니다.

### S07b — 그럴듯함 ≠ 정확함 *(신규, 유진 과정에서 가져옴)*
- 핵심 메시지: **AI는 51%짜리 답을 100%처럼 말합니다.**
- 본문: 좌측 큰 숫자 `51` (채택된 답) / 우측 `49` (예외·반대 근거, 조용히 버려짐)
- 예시 한 줄: "이 수요처는 4분기 발주가 (확실합니다 / 불확실합니다)" — 자료 없이도 둘 중 하나를 그럴듯하게 고릅니다
- 하단: 그래서 **근거 인용과 사람 검수**를 항상 붙입니다. 오늘 지시문 ⑤·⑦번이 그 장치입니다.
- 강사 노트: 영업 수치·발주 시점처럼 "틀리면 비용이 큰 것"을 예로 듭니다.

### S07c — 시작은 RACS, 익숙해지면 7블록 *(신규)*
- 핵심 메시지: 네 줄로 시작해도 됩니다.
- 본문: RACS 예시 코드블록 (Agent D 기준) + 우측에 7블록 대응표
- 하단: RACS는 7블록의 압축판입니다. 한 번 돌려보고 결과가 나오면 늘립니다.
- 강사 노트: 기초 참가자가 절반이라면 이 장에서 시간을 씁니다. 중급자는 넘어갑니다.

### S08 — IPO 명세: 프롬프트보다 먼저
- 핵심 메시지: **한 장을 먼저 채웁니다.** 이게 지시문·테스트·검수의 원본입니다.
- 본문: INPUT / PROCESS / OUTPUT / STOP / APPROVAL / TEST 6칸
- 하단: IPO가 모호하면 Agent가 아니라 업무 정의부터 다시 봅니다.

### S09 — 지시문 7블록
- 핵심 메시지: 순서를 고정하면 빠뜨리지 않습니다.
- 본문: ①역할 ②업무 범위 ③입력 검사 ④처리 순서 ⑤출력 형식 ⑥중단·보안 ⑦성공 기준·사람 승인
- 강조 박스: 지시문 끝에 항상 —
  > 근거가 없으면 추정하지 말고 질문한다. 판단·서명·발송은 사람이 한다.

### S10 — 나쁜 문장과 좋은 문장
- 핵심 메시지: **검증할 수 있게 씁니다.**
- 본문: 좌우 비교 3쌍

| ✗ | ○ |
|---|---|
| 정확하게 작성한다 | 필수 컬럼이 누락되면 질문하고 중단한다 |
| 데이터를 요약한다 | 합계를 재계산하고 표지 값과 대조한다 |
| 친절하게 답변한다 | 근거 위치를 파일·행으로 표시한다 |

### S11 — 테스트 3종
- 핵심 메시지: 정답 문장이 아니라 **행동**을 봅니다.
- 본문: 3열

| 정상 | 경계 | 실패 |
|---|---|---|
| 완전한 입력 | 합계 불일치·기준일 미지정 | 실명·권한 밖 요청 |
| 서식대로 작성 | 두 값 표시 후 질문 | 가명화 요청 후 중단 |

- 강조: **중단은 실패가 아니라 성공 행동입니다.**

### S12 — 사람이 하는 일
- 핵심 메시지: Agent는 승인 상태를 기록할 수 있지만 **승인자가 될 수 없습니다.**
- 본문: 2열 (AI: 수집·요약·계산·초안·근거 표시·누락 질문 / 사람: 사실 확정, 가격·납기 결정, 발송, 서명, 최종 책임)

### S13 — 오늘의 완주 기준
- 핵심 메시지: 완성도보다 **체인이 끊기지 않는 것**이 우선입니다.
- 본문: 2단
  - 최소 완주: IPO 1장 + v0 + 정상 테스트 1건 + 인계 파일 저장
  - 확장: v1 + 테스트 3종 + 전환 표
- 하단: 못 끝내면 `handoff/` 정답 파일로 다음 모듈을 시작합니다. 괜찮습니다.

### S15 — 지금은 이렇게 일합니다 `[팩]`
- 핵심 메시지: 문제는 도구가 아니라 **매번 다시 하는 것**입니다.
- 본문: 팀별 현행 업무 3~4단계 (scenario.md의 "지금은 이렇게 일합니다")
- B2B팀: 아침마다 뉴스를 훑고 / 신호를 찾으면 거래 이력을 열어보고 / 판단은 감으로
- 유통전략팀: 수요 데이터와 경쟁사 몰을 각각 열어보고 / 감으로 라인업을 잡고

### S16 — 오늘 만들 결과물 `[팩]`
- 핵심 메시지: 이 표를 만드는 게 목표입니다.
- 본문: `handoff/` 정답 파일의 **우선순위 표**를 그대로 캡처
- 강사 노트: 결과를 먼저 보여준 뒤 원본 CSV를 엽니다. 순서가 중요합니다.

### S17 — 입력 데이터 `[팩]`
- 핵심 메시지: 파일 두 개로 시작합니다.
- 본문: 파일명 + 행수 + 주요 컬럼 (manifest.md의 Input 스펙 열)
- 하단: 컬럼 헤더는 여러분이 사전과제에 쓴 것으로 바뀝니다.

### S18 — 실습 1: IPO 작성 (20분)
- 좌: 시간 배분 (5분 INPUT / 10분 PROCESS·OUTPUT·STOP / 5분 짝과 교환)
- 우: 체크리스트 (기준일 지정 / 필터 조건 / STOP 조건 / 우선순위 기준)
- 하단: 모호한 단어에 밑줄을 긋습니다.

### S19 — 도구 화면
- 핵심 메시지: 실행 전에 참조 파일을 다 올립니다.
- 본문: Gemini Deep Research + NotebookLM 화면 (대체: GPT 프로젝트)
- 경고 박스: **Deep Research는 1인 1회입니다.** 빈손으로 실행하면 1회가 날아갑니다.

### S20 — 실습 2: Agent v0 (35분)
- 좌: 시간 배분 (10분 지시문 7블록 / 15분 참조 파일 업로드 / 10분 정상 실행 1건)
- 우: 체크리스트

### S21 — 이 데이터의 함정 `[팩]`
- 핵심 메시지: 그냥 세면 순위가 틀립니다.
- B2B팀: 같은 고객사·같은 신호가 매체를 달리해 **중복 6건**
- 유통전략팀: `전월대비` 컬럼이 `문의건수` 추이와 **반대**로 적혀 있음 (사무서비스 193→225→278인데 '감소')
- 하단: 파생 컬럼을 믿지 말고 원본에서 다시 계산합니다.

### S22 — 실습 3: 테스트 3종 (25분)
- 본문: 3행 표 (정상 / 경계: 기준일·업종 안 주고 "분석해줘" / 실패: `*_실패.csv`)
- 강조: 실패 입력에서 프로필이 만들어지면 **통과가 아닙니다.**

## 모듈 ③ 제안자료 작성 Agent (9장)

### S23 — 모듈 표지
- 제목: ③ 제안자료 작성 Agent (Action)
- 부제: 맞춤형 영업 제안 문서 자동 생성 · 2.0h
- 산출물: `proposal_draft.md`

### S24 — 앞 단계에서 받은 것

- 본문: 체인 그림에서 ②→③ 구간 강조. `customer_profile.md` 내용 미리보기.

### S25 — 제안서 순서는 정해져 있습니다

- 본문: 4단계 + 각 단계의 근거 파일
- 하단: 두 팀 공통 확정 순서입니다. 바꾸지 않습니다.

### S26 — 공통과 팀별 `[팩]`
- 핵심 메시지: 틀은 같고 자료가 다릅니다.
- 본문: 2열
  - 공통: 제안서 순서 / 프롬프트 / 출력 형식 / 검수 기준
  - 팀별: 고객·제품 정보
- 강사 노트: 9/7 사전 모임에서 확정된 구분입니다.

### S27 — 실습 1: IPO 작성 (20분)
- 체크리스트: 독자 지정 / 제안 규모·기간 / STOP 조건
- 강조: **독자를 반드시 씁니다.** (유통전략팀은 1차 독자가 파트너입니다)

### S28 — 도구 화면
- Gemini 에이전트 + 참조 파일 (대체: GPT 프로젝트)
- 경고: 에이전트 실행은 **3회** (v0 1회 + 테스트 2회)

### S29 — 실습 2: Agent v0 (35분)
- 체크리스트: 인계 파일 / 카탈로그 / 서비스 조건 / 독자 / 규모

### S30 — 이건 절대 쓰면 안 됩니다
- 핵심 메시지: **가격·납기·할인·SLA는 확정 문구로 쓰지 않습니다.**
- 본문: 카탈로그 단가 = 참고 단가. 서비스 조건의 시간 = 참고값.
- 출력 예시: `[확인 필요] 가격·납기: 영업 담당 확정 필요`

### S31 — 실습 3: 테스트 3종 (25분)
- 본문: 실패 테스트 프롬프트를 슬라이드에 그대로 넣습니다.
