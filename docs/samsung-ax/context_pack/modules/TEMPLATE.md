# 새 모듈 만들기 — 다른 고객사·다른 차수에 이 구조를 쓰는 법

> 이 폴더의 네 모듈(A·B·C·D)은 삼성전자 B2B 영업 과정용입니다.
> **다른 고객사에 같은 과정을 하려면 방법론은 그대로 두고 모듈만 새로 만듭니다.**
> 만드는 절차는 `../../module_spec.md` 4장, 에이전트/스킬 분리는 `../common/agent_and_skill_split.md`.

---

## 0. 무엇이 그대로이고 무엇이 바뀌나

| 층 | 위치 | 고객사가 바뀌면 |
|---|---|---|
| 방법론 (프로세스·IPO·꼬리표·7블록·테스트 3종·검수) | `../common/` | **그대로** |
| 웹 환경 절차 (HTML 저장·paste·소계본·클릭 경로) | `../common/` | **그대로** |
| 업무 상황·데이터·프롬프트·정답 | `modules/<ID>/` | **교체** |

**공통층을 고치고 싶어지면 멈춰서 다시 봅니다.** 대개는 모듈 쪽에 넣어야 할 것이 공통층으로 새어 나온 경우입니다.
삼성 과정에서 시나리오가 통째로 바뀌었을 때도 공통층은 손대지 않았습니다.

---

## 1. 만들기

```bash
python3 docs/samsung-ax/tools/new_module.py E_forecast forecasting-demand-by-region
```

- 모듈 ID: 대문자 한 글자 + `_` + 소문자. 대문자는 수업 순서(A·B·C·D…)입니다.
- 스킬 이름: 소문자-하이픈 **동명사형**. 도구가 이 이름으로 스킬을 찾습니다.

`_template/`이 복사되고 이름이 채워집니다.

---

## 2. 채우는 순서 — 7단계, 하루

| 단계 | 산출 | 시간 | 놓치기 쉬운 것 |
|---|---|---|---|
| 1 요구조건서 | `00_requirement.md` | 40분 | **일 분해표를 여기서 만듭니다.** 에이전트 개수가 여기서 정해집니다 |
| 2 데이터 | `01_data/` + 소계본 | 60분 | `build_modules.py`에 builder 추가. 헤더는 요구조건서에서 읽습니다 |
| 3 프롬프트 | `02_prompt/` | 60분 | `{{ }}` 0개. ✂ 로 복사 범위 표시 |
| 4 정답 | `04_answer/` | 60분 | **실제 도구에 돌려 받습니다.** 손으로 쓰지 않습니다 |
| 5 테스트 | `03_tests/` | 40분 | 경계=질문해야 통과, 실패=중단해야 통과 |
| 6 시연 로그 | `05_demo_log.md` | 40분 | 4단계에서 오간 대화를 정리 |
| 7 마감 | `06_paste/` `07_skill/` `module.md` `CHECK.md` | 40분 | `check_module.py` 통과 |

```bash
python3 docs/samsung-ax/tools/build_modules.py E_forecast   # 2단계
python3 docs/samsung-ax/tools/check_module.py E_forecast    # 7단계
```

**정답을 다시 만들면 파생 문서가 낡습니다.** 스킬·테스트·시연 로그·모듈 카드가 인용한 금액이 정답과 어긋나는데,
읽어서는 잘 안 보입니다. 검사 12번이 이걸 대조하므로 **정답을 고칠 때마다 검사를 다시 돌립니다.**

## 3. 데이터 만들 때 지키는 것

**신호를 심고 노이즈를 섞습니다.** 신호만 있으면 누가 해도 맞히고, 노이즈만 있으면 아무도 못 맞힙니다.
삼성 네 모듈의 비율은 **신호 3할 · 노이즈 7할**입니다.

**판단을 시험하는 함정을 3~4개 넣습니다.** 계산이 아니라 판단이 갈리는 지점이어야 합니다.

| 함정의 종류 | 삼성 과정의 예 |
|---|---|
| 큰 것이 답이 아니다 | 1.2조 수주가 3순위 (시점이 멀어서) |
| 싼 것이 답이 아니다 | 경쟁사가 75만원 싼데 밝기 미달 |
| 작은 것을 버리면 안 된다 | 카페 3건은 기회 목록엔 없고 요약엔 있다 |
| 금액 순으로 보면 안 보인다 | 스탠드는 수량과 동반 구매로 봐야 2위 |
| 맞는 것이 없으면 없다고 한다 | 교육시설 담당 파트너 없음 |

**세 가지는 반드시 넣습니다.**
- 중복 (합치고 건수를 보고하는지)
- 대상 밖의 것 (필터하고 건수를 보고하는지)
- 틀린 값 또는 금지 항목 (멈추는지) → 실패 테스트 파일

**모든 값은 가상입니다.** 실제 고객사·파트너·모델명·가격·실적을 쓰지 않습니다. 제도 용어(공시 유형명 등)는 그대로 써도 됩니다.

---

## 4. 프롬프트 쓸 때 지키는 것

- **✂ 로 복사 범위를 표시합니다.** 안내 문장과 붙여넣을 지침이 섞이면 참가자가 헤맵니다.
- **`{{ }}` 자리를 남기지 않습니다.** 템플릿은 "내 업무로 전환" 단계용이고 실습에는 완성본을 씁니다.
- **금지 사항은 두 번 씁니다.** ⑥ 중단·보안에 한 번, ⑦ 성공 기준에 한 번. 한 번만 적힌 금지는 압박이 들어오면 무시됩니다.
- **대화 시작 예시 3개**를 끝에 붙입니다. 에이전트 설정에 그대로 들어갑니다.
- 단계가 여럿이면 **지침은 하나**이고 나머지는 대화 메시지입니다. 에이전트를 늘리지 않습니다.

---

## 5. 정답과 블라인드 검증

**정답은 쓰는 것이 아니라 받는 것입니다.** 실제 도구에 프롬프트와 데이터를 넣어 결과를 받고, 5분 검수를 통과시킨 것만 `04_answer/`에 둡니다.

그다음 **블라인드 검증**을 합니다.

```
정답을 모르는 사람(또는 다른 대화창)에게
프롬프트와 데이터만 준다  →  결과를 04_answer/ 와 대조한다
```

어긋나면 **데이터가 아니라 지시문을 고칩니다.** 데이터를 고쳐 맞추면 실습장에서 같은 일이 반복됩니다.
결과는 `CHECK.md`의 블라인드 검증 표에 회차별로 적습니다.

## 6. 수업에 꽂기

모듈 1개 = 2시간 = 에이전트 1개입니다. 시간 배분은 네 모듈이 같습니다.

```
프로세스·IPO 20 / 시연 15 / 실습1 30 / 실습2 25 / 실습3 15 / 전환 10 / 버퍼 5
```

- `module.md` 9절 = 슬라이드 본문
- `05_demo_log.md` = 도입 시연 15분
- `03_tests/` = 실습 2·3
- `04_answer/` = 못 따라온 참가자의 진입로
- `00_requirement.md` 일 분해표 = 강의 20분

**단계가 하나인 모듈을 첫 모듈로 놓습니다.** 실습이 짧아 남는 시간에 설계 6단계를 가르칠 수 있습니다.

## 7. 자주 하는 실수

| 실수 | 왜 문제인가 |
|---|---|
| 요구조건서 없이 데이터부터 만듦 | 헤더가 흔들리고 정답이 데이터에 끌려다닙니다 |
| 단계마다 에이전트를 따로 만듦 | 2시간에 안 끝납니다. 🔒이 없으면 단계입니다 |
| 정답을 손으로 씀 | 참가자 결과와 대조가 안 됩니다 |
| 함정 없이 깨끗한 데이터 | 누가 해도 맞혀서 검수 훈련이 안 됩니다 |
| 실패 테스트가 없음 | **중단하는 법을 안 가르치면 업무에 못 씁니다** |
| 금지를 한 곳에만 씀 | 압박이 들어오면 밀립니다. ⑥ 중단·보안과 ⑦ 성공 기준 **두 곳**에 씁니다 |
| 거절만 하고 끝냄 | 사용자가 다른 경로로 같은 것을 요구합니다. **대신 줄 수 있는 것**을 함께 줍니다 |
| 동점 처리에 하한이 없음 | 1%p 차이로 수백만 원이 뒤집힙니다. 뒤집는 조건에 **최소 격차**를 둡니다 |
| paste 파일이 6KB를 넘음 | 업로드가 막힌 참가자가 실습을 못 합니다 |

### 블라인드 검증에서 실제로 나온 결함 다섯 가지

삼성 네 모듈을 블라인드로 돌려 나온 것입니다. 전문은 [`../../validation_log.md`](../../validation_log.md).

1. **자동 검사 통과는 완성이 아닙니다.** 11항목은 파일과 헤더를 봅니다. 지시문의 빈틈은 못 봅니다.
2. **판단 기준이 둘 이상이면 순서를 적습니다.** "규모와 시기로 정렬한다"는 둘이 엇갈릴 때 답이 갈립니다.
3. **분류 값은 전부 열거합니다.** 값이 둘뿐이면 셋째 경우가 올 때 실행자가 값을 만들어 냅니다.
4. **데이터가 지시문을 만족시킬 수 있는지 먼저 확인합니다.** 데이터상 불가능한 것을 요구하는 규칙이 실제로 있었습니다.
5. **"없을 때"를 반드시 씁니다.** 값이 없을 때, 대안이 없을 때, 맞는 것이 없을 때. 이 셋이 결함의 대부분이었습니다.
6. **기준본은 규칙에서 계산해 만듭니다.** 답을 먼저 정하고 규칙을 나중에 쓰면 둘이 어긋납니다.
   삼성 과정에서 이 실수가 **네 번** 나왔습니다. 규칙을 쓴 뒤 그 규칙대로 계산해 기준본을 뽑고, 둘이 같은지 확인하십시오.
