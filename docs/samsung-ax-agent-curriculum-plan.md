## 0. 설계 원칙 — "컨텍스트는 데이터다"

이 과정의 교안은 **슬라이드 + 에이전트 골격 + 컨텍스트 데이터 팩**의 3층으로 만든다. 핵심은 팀·업무·도구에 관한 모든 맥락을 **프롬프트나 슬라이드 본문에 박지 않고, 파일(데이터)로 분리**하는 것이다.

| 층 | 내용 | 팀별로 바뀌는가 |
|---|---|---|
| ① 방법론 슬라이드 | Agent 개념, IPO 명세, 지시문 7블록, 테스트 3종, 사람 승인 | 아니오 (공통) |
| ② 에이전트 골격 | 3개 Agent의 지시문 템플릿, 출력 양식, STOP 규칙 | 아니오 (공통) |
| ③ 컨텍스트 데이터 팩 | 팀 프로필, 더미 데이터, 양식, 테스트 케이스 | **예 (B2B팀 / B2B유통전략팀)** |

이렇게 하면 9/3 메일의 첫 번째 질문(두 팀 업무를 모두 반영할 수 있는가)이 "에이전트를 6개 만드는 문제"가 아니라 "데이터 팩을 2벌 만드는 문제"로 바뀐다. 사내강사가 9차수를 운영할 때도 슬라이드는 그대로 두고 데이터 팩만 교체하면 된다.

컨텍스트를 데이터로 다루는 세 가지 규칙:
1. **팀 프로필은 `team_profile.md`로.** 9/4 메일의 경로·품목·관리항목을 그대로 구조화한다. GPT 프로젝트 파일 / NotebookLM 소스로 넣는다.
2. **더미 데이터는 CSV·XLSX·MD로.** 에이전트는 "아는 것"이 아니라 "받은 파일"로 일한다. 근거 없는 수치 생성 금지 규칙과 짝을 이룬다.
3. **사전과제도 데이터로.** 후보 강사의 사전과제를 자유 서술이 아닌 필드형 양식으로 받아 JSON/CSV로 정리하고, 핏코치로 필터링한 뒤 더미 데이터 생성의 입력으로 쓴다.

## 1. 확정 제약 (메일에서 추출)

### 1.1 도구 환경 (8/18)
| 항목 | GPT | Gemini |
|---|---|---|
| 사용 가능 | 프로젝트, GPTs | NotebookLM, Deep Research, 에이전트 기능 |
| 사용 불가 | 플러그인, Codex(실습 제외) | **Gems**, CLI(실습 제외) |
| 실습 모델 | Instant 중심 (Thinking/Pro 월 ~10크레딧) | Flash 중심 (Pro 제한) |
| 횟수 제한 | 추론 모델 제한적 | 기능별 월 ~10회 |
| 데이터 | 개인정보·기밀 제외 사내 데이터 업로드 가능 | 동일 |
| 비중 | 50:50 계획 → 재무 측 "Gemini 100%" 요청 추가 | |

설계 시사점:
- **Gems 불가**가 가장 큰 제약. Gemini 쪽 "저장된 에이전트"는 NotebookLM(지식 컨테이너) + 저장 프롬프트 파일(`agent_prompt.md`)로 대체한다. 이것 자체가 "컨텍스트=데이터" 원칙과 맞다.
- 월 10회 제한 → Deep Research·NotebookLM 실행 횟수를 교안에 **예산으로 명시**(예: 1인 Deep Research 1회, NotebookLM 노트북 1개).
- Instant/Flash 중심 → 긴 추론보다 **명확한 IPO + 파일 근거**로 품질을 내는 설계. 가톨릭대 교안 방식 그대로 적용 가능.
- GPT/Gemini 비중은 **Agent별로 주도구를 나눈다**(아래 3장). 재무 측 Gemini 100% 요청은 데이터 팩이 도구 중립이므로 "같은 실습을 Gemini만으로도 완주 가능"한 경로를 병기해 대응.

## 2. 9/3 메일의 3가지 질문에 대한 답 (기획 방향)

### Q1. 두 팀 업무를 모두 반영하는 양성과정 구성이 가능한가?
**가능. 단, "공통 Agent 3개 + 팀별 데이터 팩 2벌" 구조로.**
- 김승진 프로의 판단대로 제안자료 작성 Agent는 공통. 시장·고객 분석, 데이터 분석도 골격은 공통이고 **입력 데이터와 관리 지표만 다르다**.
- 양성과정 1일차는 후보 강사를 팀 기준으로 2그룹(A: B2B팀 팩, B: 유통전략팀 팩)으로 나눠 **같은 슬라이드, 다른 데이터**로 진행. 강사는 한 번만 가르치고, 후보들은 자기 팀 맥락에서 체험한다.
- 준비 범위 증가분은 "데이터 팩 1벌 추가"로 한정된다. 슬라이드·지시문·루브릭은 늘지 않는다.

### Q2. 사전과제에서 구현 방식·결과물 형태를 어느 수준까지 지정할 것인가?
**업무·요구사항·데이터 명세까지는 필수로 받고, 구현 방식은 "메뉴 중 선택"으로 열어둔다.**
- 필수 필드(데이터로 수집): 업무 한 문장, 반복 빈도, 입력 자료(파일명·형식·열), 출력물(양식·독자), 사람이 판단·승인하는 지점, 금지 데이터.
- 선택 필드: 희망 도구(GPT 프로젝트 / GPTs / NotebookLM / Deep Research), 희망 결과물 형태(표 / 보고서 초안 / HTML 대시보드).
- 이유: 구현 방식은 도구 제약(Gems 불가, 모델 제한)에 따라 강사가 교육 중 조정해야 하므로, 사전에 고정하면 오히려 재작업이 생긴다. 반면 데이터 명세가 없으면 더미 데이터를 만들 수 없다.
- GPT '프로젝트' 필수 여부: **제안자료 Agent에 한해 권장**(참조 파일 다수 → 프로젝트가 적합). 다른 Agent는 도구 자유.
- 사전과제 결과는 핏코치(Agent-Task Fit 6기준)로 걸러 **양성과정 시범강의 주제 4개**(메인 강사 후보 4명 × 1주제)를 선정한다.

### Q3. 본 과정 10/1, 10/2 각 1차수 운영 가능한가?
강사 일정 확인 사항(본 문서에서는 결정하지 않음). 가능하다면 1차수(10/1)에 사내강사 참관, 2차수(10/2)는 사내강사 1명이 한 모듈을 공동 진행하는 "핸드오버 차수"로 쓰는 것을 제안.

## 3. 본 과정 교안 설계 (강사 담당 6시간)

### 3.1 Agent별 도구 배분과 재사용 자산
| 모듈 | 주 도구 | 보조/대체 경로(Gemini 100% 대응) | 재사용할 기존 자산 |
|---|---|---|---|
| ② 시장·고객 분석 Agent | **Gemini** Deep Research + NotebookLM | GPT 프로젝트 + 웹검색 | 삼성 GPTS 영업비서 교안의 "고객사 분석·페르소나" 프롬프트, 제안커리큘럼의 리뷰 수집→정규화 흐름 |
| ③ 제안자료 작성 Agent | **GPT** 프로젝트(+GPTs) | NotebookLM 소스 + 저장 프롬프트 | 삼성 GPTS 영업비서 교안의 S.T.I.C JD, 세일즈 시뮬레이션 페르소나; 가톨릭대 교안의 지시문 7블록·지식파일 규칙 |
| ④ 데이터 분석 Agent | **GPT** 데이터 분석(파일 업로드) | Gemini Flash 파일 분석 + NotebookLM | 제안커리큘럼의 감성분석·대시보드·전략보고서 흐름(바이브코딩 부분 제외), 삼라 Gemini 주간보고 자동화 패턴 |

공통 방법론(세 모듈 동일): **IPO 명세 → 지식(데이터) 연결 → 지시문 → 테스트 3종(정상·경계·실패) → 사람 승인 지점 → 배포 체크**. 가톨릭대·동국대 교안의 구조를 그대로 가져오되, 대학 행정 예시를 B2B 영업 예시로 치환한다.

### 3.2 모듈별 2시간 타임라인 (공통 골격)
```
00~15  개념·시연 (강사): 이 Agent가 하는 일, IPO 한 장, 오늘 데이터 팩 소개
15~35  실습 1: 데이터 팩 열고 team_profile + 입력 데이터 확인, IPO 작성
35~70  실습 2: 도구에서 v0 제작 (지시문 7블록 붙여넣기, 파일 업로드)
70~95  실습 3: 테스트 3종 실행, 테스트 로그 기록, v1 수정
95~110 짝 시연·피드백 (정상 1건 + 실패 1건만)
110~120 내 업무 전환: "부서·데이터·승인자만 교체" 표 작성
```
보조강사 3명 배치: 모듈당 17명 내외씩 담당, 동국대 강사 가이드의 "실습 시간엔 기립 순회, 이석자 복귀 안내" 원칙 적용.

### 3.3 Agent별 실습 시나리오 (팀별 데이터 팩으로 분기)

**② 시장·고객 분석 Agent — "정보 센싱"**
| | B2B팀 팩 | B2B유통전략팀 팩 |
|---|---|---|
| 시나리오 | 대형 건설사 분양 단지 SAC 입찰 대응 | 명절 복지몰 시즌 파트너 제안 대상 발굴 |
| 입력 데이터 | `bids.csv`(입찰공고 더미), `market_price.csv`, `voc.csv`, `key_accounts.csv` | `partners.csv`(파트너 실적), `welfare_mall_events.csv`, `smb_segments.csv` |
| 출력 | 고객 프로필 1장 + LEAD/BO 후보 표 + 근거 출처 | 파트너별 공략 우선순위 표 + 근거 |
| STOP | 출처 없는 시장 수치, 실명 담당자 정보 | 파트너 계약 조건 추정 |

**③ 제안자료 작성 Agent — "맞춤 제안"**
| | B2B팀 팩 | B2B유통전략팀 팩 |
|---|---|---|
| 시나리오 | 대기업 사옥 HVAC+모바일 통합 제안 | 중소기업 대상 월 구독 + DMFP 유지보수 번들 제안 |
| 입력 데이터 | `proposal_template.md`, `product_catalog.csv`, `customer_requirements.md` | 동일 골격 + `subscription_plans.csv`, `dmfp_service.md` |
| 출력 | 제안서 초안(양식 매핑) + 확인 필요 목록 | 파트너 배포용 제안서 초안 |
| STOP | 가격·납기 확정 문구, 할인율 생성 | 동일 |

**④ 데이터 분석 Agent — "현황 보고"**
| | B2B팀 팩 | B2B유통전략팀 팩 |
|---|---|---|
| 시나리오 | 주요 고객 품목 확대 현황 + LEAD/BO 파이프라인 월보 | 대형 파트너 매출·구독 해지율 월보 |
| 입력 데이터 | `sales_monthly.xlsx`(SCM/ERP 형태 더미), `pipeline.csv`, `report_template.md` | `partner_sales.xlsx`, `subscriptions.csv`, `report_template.md` |
| 출력 | 트렌드 요약 + 특이사항 + 근거표 + 보고서 초안 | 동일 |
| STOP | 합계 불일치, 기준월 미지정, 실명 포함 | 동일 |

각 팩에는 `test_cases/` 폴더에 **정상·경계·실패 입력 3종**을 반드시 넣는다(동국대 실습팩 방식). 경계 예: 표지 합계와 상세 합계 불일치. 실패 예: 고객 담당자 실명·연락처 포함.

## 5. 사내강사 양성과정 (9/16~17) 설계

### 1일차 — 본 과정 체험 (17명, 2그룹)
- 오전: ①②, 오후: ③④ 를 본 과정과 동일 타임라인으로 진행. 삼성 자체 운영 모듈(①⑤)은 축약 시연으로 대체.
- 그룹 A(B2B팀 팩) / 그룹 B(유통전략팀 팩). 메인 강사 후보 4명은 양 그룹에 2:2 배치해 두 팩을 모두 본다.

### 2일차 — 시범강의 + 피드백
- 메인 강사 후보 4명 × 1.5h. 주제는 사전과제 → 핏코치 필터 → 4개 선정.
- 나머지 후보는 교육생 페르소나 부여(B2B/유통, 초급/중급 조합 4종).
- 피드백 기준: 동국대 루브릭(입력 명확성 15 / 처리 재현성 20 / 출력 행동성 15 / 중단 조건 20 / 사람 승인 15 / 테스트 기록 15, 안전 항목 0점이면 재작성)을 **강의 평가용으로 변형**: "데이터 팩을 제대로 열게 했는가 / IPO를 쓰게 했는가 / 테스트 3종을 돌리게 했는가 / 실패 시 멈추게 했는가".
- 보조강사(스파르타)는 1일차 종일 + 2일차 오전(0.5일)만 요청 → 9/3 메일의 "1일 또는 1.5일" 중 **1.5일 권장**.

## 6. 사전과제 양식 (제안) — 데이터로 수집

| 필드 | 필수 | 예시(B2B팀) |
