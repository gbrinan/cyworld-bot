# 일을 보는 법 — 프로세스 → IPO → 에이전트 경계

> **이 과정의 첫 시간입니다.** 지시문 7블록보다 먼저 옵니다.
> 에이전트를 못 만드는 이유는 프롬프트를 못 써서가 아니라, **지금 일이 어떻게 흘러가는지 적어 본 적이 없기** 때문입니다.
> 여기서 나온 표가 그대로 지시문이 됩니다. 도구로 옮기는 단계는 `agent_and_skill_split.md`에서 이어집니다.

---

## 0. 전체 순서

```
①  As-Is 프로세스        지금 일이 어떻게 흘러가는가        ← 여기서 시작
②  단계별 IPO            각 단계가 무엇을 받아 무엇을 내놓나
③  꼬리표                🔒 사람만 / ✍️ AI 초안 / ⚙️ AI 반복 / 🔌 밖에서
④  묶기                  에이전트 경계와 개수가 정해진다
─────────────────────────────────────────────────
⑤  에이전트 / 스킬 분리   agent_and_skill_split.md
⑥  지시문 7블록 · SKILL.md
```

①~④가 이 문서입니다. **④가 끝나면 에이전트 개수와 경계가 이미 정해져 있습니다.** 남은 것은 옮겨 적는 일입니다.

---

## 1. ① As-Is 프로세스 — 지금 일이 어떻게 흘러가는가

**바꾸기 전에 그립니다.** 이상적인 절차가 아니라 **지금 실제로 하는 대로** 적습니다.

| 칸 | 적는 것 |
|---|---|
| 단계 | 동사 하나. "찾아서 정리한다"는 두 단계입니다 |
| 누가 | 나 / 동료 / 다른 팀 / 고객 |
| 시간 | 이 단계에 실제로 걸리는 시간 |
| 막히는 곳 | 기다림·반복·헷갈림이 생기는 지점 |

5~10단계면 적당합니다. 3단계면 너무 뭉쳤고, 20단계면 너무 잘게 갔습니다.

### 여기서 이미 보이는 것

- **시간이 몰린 단계** — 여기가 후보입니다. 전체의 절반을 먹는 단계가 대개 하나 있습니다.
- **사람이 바뀌는 지점** — 넘기고 기다리는 곳입니다. 파일로 넘어가는지 말로 넘어가는지 봅니다.
- **같은 일을 두 번 하는 곳** — 옮겨 적기, 형식 바꾸기. 거의 항상 ⚙️입니다.

```
✗  영업을 효율화한다           ← 프로세스가 아닙니다
✗  AI로 업무를 자동화한다       ← 무슨 일인지 없습니다
○  요구조건 메일을 받는다 → 조건을 표로 적는다 → 모델을 찾는다 → …
```

## 2. ② 단계별 IPO — 받는 것 / 하는 일 / 내놓는 것

프로세스의 각 단계를 세 칸으로 엽니다.

| I (Input) | P (Process) | O (Output) |
|---|---|---|
| 이 단계를 시작하려면 **손에 무엇이 있어야 하나** | 그것으로 무엇을 하나 | 끝나면 **무엇이 남나** |

### 규칙 세 가지

**하나. Input은 꺼낼 수 있는 것이어야 합니다.**

```
○  요구조건 메일 · 가격가이드 엑셀 · 화면에서 복사한 표 · 내가 답한 질문
✗  "내 경험" · "감" · "지난번에 했던 기억"
```

Input이 내 머릿속이면 그 단계는 지금 에이전트로 못 만듭니다. **머릿속을 파일로 꺼내는 것이 먼저**입니다.
꺼내는 방법은 둘입니다. 문서로 적어 두거나, **에이전트가 질문해서 받거나**. A 모듈의 A-2가 두 번째 방법입니다.

**둘. Output은 다음 단계가 받을 수 있는 모양이어야 합니다.**

화면에 보이는 글이 아니라 **파일 이름과 형식**으로 적습니다. `고객 프로필 정리` 가 아니라 `customer_profile.md`입니다.

**셋. 앞 단계의 O와 다음 단계의 I가 다르면, 거기서 사람이 손으로 바꾸고 있습니다.**

```
3단계 O : 화면에서 복사한 뒤죽박죽 텍스트
4단계 I : [수요처명][모델명][온라인가격][제품spec.] 4열 표
              ↑ 이 사이를 사람이 메우고 있습니다
```

**이 틈이 에이전트 자리입니다.** C 모듈의 프롬프트 ⓪이 정확히 이 틈에서 나왔습니다.
틈을 찾았으면 두 가지 중 하나를 합니다. 틈을 메우는 에이전트를 만들거나, **앞 단계의 O 형식을 바꿔** 틈을 없앱니다.

## 3. ③ 꼬리표 붙이기

단계마다 네 가지 중 하나를 답니다.

| 꼬리표 | 뜻 | 판단 기준 |
|---|---|---|
| 🔒 **사람만** | AI에게 넘기지 않는다 | 대외 확정, 가격·납기, 책임이 따르는 판단, 승인 |
| ✍️ **AI 초안** | AI가 쓰고 사람이 검수 | 매번 내용이 달라지고 판단이 섞임 |
| ⚙️ **AI 반복** | 규칙이 고정되어 매번 같다 | 형식 변환, 추출, 집계, 정렬 |
| 🔌 **밖에서 가져옴** | 사람이 가져와 올린다 | 사내 시스템, 외부 사이트, 파일 |

**헷갈리면 이렇게 묻습니다.** "이 단계가 틀렸을 때 누가 책임지는가." 내가 책임지면 🔒입니다.

IPO를 먼저 적었으면 꼬리표가 쉽게 붙습니다. **Input과 Output이 매번 같은 형식이면 ⚙️**, Output이 매번 달라지면 ✍️입니다.

---

## 4. ④ 묶기 — 에이전트 개수가 정해집니다

```
붙어 있는 ✍️ ⚙️ 단계들     →  에이전트 1개
🔒 단계                    →  에이전트 경계. 여기서 사람에게 넘긴다
🔌 단계                    →  입력 파일. 에이전트 안이 아니라 앞에 놓인다
```

**🔒가 중간에 끼면 반드시 잘립니다.** 하나로 묶으면 사람이 확인해야 할 지점을 AI가 지나쳐 버립니다. 이건 안전 문제라 선택이 아닙니다.

### 🔒이 없는데 성격이 다르면 — 나누지 말고 단계로 둡니다

```
🔒 가 끼어 있다      →  에이전트를 나눈다          (안전. 선택 아님)
🔒 가 없다           →  한 에이전트 안의 단계로    (에이전트는 하나로 유지)
```

C 모듈은 수집 정제·모델 추출·비교 제안이 서로 다른 일이지만 사이에 🔒이 없습니다. 그래서 **에이전트는 하나이고 프롬프트가 셋**입니다.
A 모듈도 수집·되묻기·판단 셋이지만 에이전트는 하나입니다.

**에이전트를 늘리면 관리할 것만 늘어납니다.** 참조 파일을 세 곳에 올리고, 셋을 따로 고치고, 결과를 사람이 옮겨 나릅니다.
이 과정의 네 모듈은 전부 **에이전트 1개 + 단계 1~3개**입니다.

| 모듈 | 에이전트 | 단계 | 왜 |
|---|---|---|---|
| D 데이터 분석 | 1 | 1 | 점검~근거까지 한 흐름 |
| C 제안자료 | 1 | 3 | 정제 / 추출 / 제안. 사이에 🔒 없음 |
| A Sensing 직판 | 1 | 3 | 수집 / 프로파일 / 분석. 사이에 🔒 없음 |
| B Sensing 경로 | 1 | 3 | 키워드 / 추출 / 보고서. 삼성 요구 프롬프트 3종 |

### 묶음이 지시문이 되는 자리

| 분해표에서 | 지시문 7블록에서 |
|---|---|
| 묶음이 하는 일을 한 문장으로 | ① 역할 |
| 묶음에 들어간 단계 / 안 들어간 단계 | ② 업무 범위 (하는 일 / 하지 않는 일) |
| 묶음 첫 단계의 **I** | ③ 입력 검사 |
| 묶음 안 단계들의 **P**, 순서 그대로 | ④ 처리 순서 |
| 묶음 마지막 단계의 **O** | ⑤ 출력 형식 |
| 묶음 **바로 뒤**의 🔒 단계 | ⑥ 중단 · ⑦ 사람 승인 |

**"하지 않는 일"은 지어내는 것이 아닙니다.** 이 묶음에 안 들어간 단계가 그대로 들어갑니다.

### ② 단계별 IPO + ③ 꼬리표

| # | I | P | O | 꼬리표 |
|---|---|---|---|---|
| 2 | 요구조건 메일 | 조건 6항목을 뽑는다 | `customer_request.md` | ✍️ |

**3단계의 O(뒤죽박죽 텍스트)와 4단계의 I가 같습니다.** 이어져 있습니다.
**2단계의 O와 5단계의 I도 이어집니다.** 대신 4단계와 5단계 사이에 사람이 손으로 하던 옮겨적기가 있었고, 그게 40분이었습니다.

### ④ 묶기

```
 3번 🔌            →  입력 (사람이 화면에서 가져옴)
 4번 ⚙️            →  단계 ⓪  수집 정제
 2·5번 ✍️⚙️        →  단계 ①  요구조건 분석 + 모델 추출      ┐ 에이전트 1개
 6·7번 ✍️          →  단계 ②  비교 + 3안 제안                ┘
 8·9번 🔒          →  ⑥ 중단 · ⑦ 승인 ("확정 견적서는 만들지 않는다")
```

**C 모듈의 프롬프트가 셋인 이유가 여기서 나왔습니다.** 우리가 정한 것이 아니라 일이 그렇게 생겼습니다.
실패 테스트("확정 견적서 만들어줘")가 8번 단계인 것도 마찬가지입니다.

## 7. 쪼갠 뒤에 고르는 기준 — 다 만들지 않습니다

첫 번째로 만들 묶음은 이 셋을 다 만족해야 합니다.

1. **자주 한다** — 주 1회 이상. 1년에 두 번 하는 일은 만드는 시간이 더 듭니다.
2. **Input이 파일로 손에 있다** — 2장의 첫 번째 규칙입니다.
3. **틀려도 되돌릴 수 있다** — 초안이라 사람이 고치면 되는 것.

셋 중 하나라도 아니면 다음 묶음으로 넘어갑니다. `fit_check.md`의 CANNOT 7항목과 함께 봅니다.

**시간이 가장 많이 걸리는 단계가 1순위는 아닙니다.** C 모듈에서 가장 오래 걸리는 3단계(90분)는 🔌라서 에이전트가 못 됩니다. 대신 그 다음 4단계(40분)가 됩니다.

## 8. 워크북에 쓰는 빈 표

내 업무로 옮길 때 채웁니다. 워크북 부록에 같은 표가 있습니다.

```
① As-Is 프로세스
   #  단계                          누가        시간     막히는 곳
   1  ____________________________  ________  ______  ____________
   2  ____________________________  ________  ______  ____________
   3  ____________________________  ________  ______  ____________
   4  ____________________________  ________  ______  ____________
   5  ____________________________  ________  ______  ____________

② 단계별 IPO + ③ 꼬리표
   #   I (받는 것)          P (하는 일)        O (내놓는 것)       꼬리표
   1   __________________  __________________  __________________  [🔒✍️⚙️🔌]
   2   __________________  __________________  __________________  [🔒✍️⚙️🔌]
   3   __________________  __________________  __________________  [🔒✍️⚙️🔌]
   4   __________________  __________________  __________________  [🔒✍️⚙️🔌]
   5   __________________  __________________  __________________  [🔒✍️⚙️🔌]

   O와 다음 I가 다른 곳 : ___번과 ___번 사이     ← 에이전트 자리

④ 묶기 : 에이전트 ___개 / 경계(🔒) ___번 / 입력(🔌) ___번

⑤ 첫 번째로 만들 것 : 에이전트 ___
   □ 주 1회 이상   □ Input이 파일로 있음   □ 틀려도 되돌릴 수 있음
```

**강사는 이 표를 걷어서 봅니다.**

| 신호 | 뜻 |
|---|---|
| 꼬리표가 전부 ✍️ | 아직 쪼개지 않았습니다 |
| 🔒이 하나도 없음 | 대외로 나가는 단계를 빠뜨렸습니다 |
| Input에 "경험"·"감" | 머릿속을 먼저 꺼내야 합니다 |
| O와 다음 I가 전부 같음 | 손으로 메우던 틈을 못 찾은 것입니다. 다시 봅니다 |
