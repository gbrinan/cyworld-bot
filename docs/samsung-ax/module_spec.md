# 모듈 방식 제안 — 요구조건서 한 장으로 Agent 모듈을 만든다

> 요청: "각 에이전트를 만드는 것이 모듈로 동작해야 해. 요구조건에 따라 모듈을 만드는 것으로 제안해줘"
> 작성 2026-09-11 · 근거: `agent_structure_v2.md`(삼성 9/7 양식 4개), `handoff_review.md`(P0 F1·F2·F3, P1 F4·F7)

---

## 0. 한 장 요약

**Agent 하나 = 폴더 하나 = 닫힌 단위(모듈).** 모듈은 `00_requirement.md`(요구조건서) 한 장에서 출발하고, 어느 Agent든 같은 7단계 빌드 절차로 만듭니다. 삼성 양식 4개 → 요구조건서 4장 → 모듈 4개.

```
요구조건서 1장  ──7단계 빌드──▶  모듈 1개 (데이터·프롬프트·테스트·정답·시연로그·인계)
                                    └─ CHECK.md 12항목 통과 = 완성
```

모듈이어야 하는 이유 세 가지입니다.

| 필요 | 모듈이 해결하는 방식 |
|---|---|
| 김승진 프로 요청 "Agent별 순차 공유" (9/9) | 모듈 폴더 하나를 zip으로 보내면 그 Agent는 끝. 다른 모듈 상태와 무관 |
| 진도 편차 — 앞 실습을 못 끝낸 참가자 | 모든 모듈은 자기 `01_data/`만으로 단독 실행. 앞 모듈 결과가 없어도 시작 |
| 9차수 운영·다른 팀 확장 | 요구조건서만 새로 쓰면 같은 절차로 새 모듈. 방법론(`common/`)은 손대지 않음 |

"컨텍스트는 데이터다"를 한 단계 더 내린 것입니다. 지금까지는 **방법론 / 데이터 팩**의 2층이었고, 이제 데이터 팩 안에서도 **요구조건서가 원본, 나머지는 파생물**입니다.

## 1. 모듈의 구조

```
context_pack/modules/<모듈ID>/
├─ 00_requirement.md     요구조건서 — 모듈의 유일한 원본. 삼성 양식 5항목 + 파생 규칙용 메타
├─ module.md             모듈 카드 1장 — 강사·참가자가 처음 보는 문서 (입력/출력/도구/시간/다음)
├─ 01_data/              입력 데이터 (삼성 지정 헤더 그대로) + *_소계.csv
├─ 02_prompt/            완성 프롬프트 — {{ }} 자리 0개, 그대로 붙여넣기. 대화 시작 예시 3개 포함
├─ 03_tests/             test_normal.md · test_boundary.md · test_failure.md (입력 + 기대 행동 + 통과 기준)
├─ 04_answer/            정답 산출물 — 실제로 도구에 돌려 받은 결과 (.html / Word 붙여넣기용 .md)
├─ 05_demo_log.md        시연 로그 — 올린 파일·붙여넣은 프롬프트·첫 응답 확인 3개·되묻기 문장
├─ 06_paste/             01_data의 마크다운 표 버전 (업로드 막힐 때). 파일당 6KB 이하
└─ CHECK.md              완성 판정 12항목. tools/check_module.py 가 자동 검사분을 채움
```

모듈 ID는 `D_analysis` `C_proposal` `A_sensing_b2b` `B_sensing_partner`. 폴더 안 파일명은 네 모듈이 **완전히 같습니다.** 강사가 D를 한 번 운영해 보면 C·A·B의 어디에 무엇이 있는지 압니다.

## 2. 요구조건서 — 모듈의 유일한 입력

`00_requirement.md`는 두 부분입니다. 위쪽 frontmatter(기계가 읽는 값)와 아래쪽 본문(삼성 양식 원문).

| frontmatter 필드 | 내용 | 어디서 오나 |
|---|---|---|
| `module` `name` | 모듈 ID, SKILL.md에 쓸 이름(소문자-하이픈 동명사형) | 우리가 정함 |
| `source` | 삼성 양식 번호와 날짜 | 9/7 pptx |
| `team` | `common` / `b2b` / `partner` | 양식 1-1·1-2·2·3 |
| `tool.primary` `tool.backup` | 주 도구·대체 도구 (모델명까지) | 8/18 안내 + 9/11 캡처 |
| `inputs[]` | 파일명, **헤더 리스트(삼성 지정 원문 그대로)**, 행 수, 형식 | 양식 "Input" 칸 |
| `outputs[]` | 파일명, 형식(html/docx-paste), **섹션 순서** | 양식 "Output" 칸 |
| `process[]` | 처리 순서 (양식 "Agent 활용" 칸) | 양식 |
| `verticals` | 버티컬 목록 | 양식 1-2·3 |
| `planted[]` | **정답이 나오도록 데이터에 심는 신호.** 예: "호텔 버티컬에서 HX-55T + 스탠드 조합이 3회 반복" | 우리가 설계 |
| `tests` | 정상·경계·실패 한 줄 정의 | `common/test_cases_guide.md` 패턴 |
| `subtotals` | 소계본 축과 합계 컬럼 (코드 실행 불가 대비) | 데이터 설계 |
| `chain.in` `chain.out` | 앞·뒤 모듈과 주고받는 파일 (선택) | 6장 |
| `forbidden[]` | 이 모듈 어디에도 있으면 안 되는 문자열 (v1 품목명, 실제 고객명 등) | 보안 규칙 |
| `confirm[]` | 삼성에 확인 중인 항목 — 답이 오면 이 필드만 고치고 재빌드 | `agent_structure_v2.md` 8장 |

**규칙: 요구조건서에 없는 것은 모듈에 들어가지 않습니다.** 데이터에 컬럼을 하나 더 넣고 싶으면 먼저 `inputs[].headers`를 고칩니다. 그래야 삼성이 헤더를 바꿔 보내왔을 때 어디를 고쳐야 하는지 한 곳입니다.

## 3. 요구조건 → 산출물 파생 규칙

요구조건서의 값이 하위 파일의 어느 자리로 가는지 고정합니다. 이 표가 "요구조건에 따라 모듈을 만든다"의 실체입니다.

| 요구조건서 필드 | 파생되는 곳 | 방법 |
|---|---|---|
| `inputs[].headers` | `01_data/*.csv` 1행 | **문자 하나까지 동일.** check_module.py가 대조 |
| `inputs[].headers` | 프롬프트 **③ 입력 검사** 표 | "필수 컬럼: [판매일자] [버티컬] …" 로 복사 |
| `inputs[].rows` | 데이터 행 수, `06_paste/` 크기 | 행 수 × 열 수로 6KB 이내 확인 |
| `outputs[].sections` | 프롬프트 **⑤ 출력 형식** | 섹션 순서 그대로 HTML 헤딩(`<h2>`)이 됨 |
| `outputs[].file` | `04_answer/` 파일명, `05_demo_log.md` 저장 단계 | 동일 파일명 |
| `process[]` | 프롬프트 **④ 처리 순서** | 삼성 양식의 ①②③④ 번호를 유지 |
| 본문 "업무 상황" | 프롬프트 **① 역할** + 모듈 카드 첫 문단 + 슬라이드 "지금은 이렇게 일합니다[팀별]" | 원문 요약 |
| `planted[]` | `01_data/` 값 생성 규칙 + `04_answer/` 정답의 근거 행 | 심은 신호가 정답에 나타나야 통과 |
| `tests` | `03_tests/` 3파일 | 경계=질문해야 통과, 실패=중단해야 통과 |
| `subtotals` | `01_data/*_소계.csv` | 세 축 합계 == 상세 합계 (자동 검산) |
| `tool` | 모듈 카드 "도구" 칸, `05_demo_log.md` 클릭 경로 | `tool_paths.md` 참조 |
| `forbidden[]` | 모듈 전체 grep | 하나라도 나오면 CHECK 실패 |
| `name` | SKILL.md `name`, 워크북 "내 업무로 전환" 예시 | 그대로 |

프롬프트 7블록 중 **② 업무 범위·⑥ 중단·보안·⑦ 성공 기준**은 요구조건서에서 직접 파생되지 않고 `common/methodology.md`·`security_rules.md`에서 옵니다. 이 셋이 네 모듈에서 거의 같은 문장이라는 점이 공통층이 살아 있다는 증거입니다.

## 4. 빌드 절차 — 요구조건서에서 완성 모듈까지 7단계

한 모듈에 **작업일 1일**(약 6h)을 잡습니다. 순서를 바꾸지 않습니다. 4단계에서 정답이 안 나오면 2단계로 돌아갑니다.

| 단계 | 산출 | 시간 | 핵심 판단 |
|---|---|---|---|
| **1 요구조건서** | `00_requirement.md` | 40분 | 삼성 양식을 옮기고 `planted` `tests` `subtotals`를 설계. 확인 중인 항목은 `confirm[]`에 두고 가정값으로 진행 |
| **2 데이터** | `01_data/` + 소계본 | 60분 | `tools/make_dummy_data.py`에 모듈별 builder 추가. 헤더는 요구조건서에서 읽음. planted 신호를 심되 노이즈 행을 70% 이상 섞음 |
| **3 프롬프트** | `02_prompt/` | 60분 | 3장 파생 규칙대로 7블록을 채움. `{{ }}` 0개. 대화 시작 예시 3개 |
| **4 정답** | `04_answer/` | 60분 | **주 도구(GPT Instant)에 실제로 돌려** 결과를 받고 5분 검수를 통과시킴. 대체 도구(Gemini Flash)에서도 planted 신호가 잡히는지 1회 확인 |
| **5 테스트** | `03_tests/` | 40분 | 경계·실패 입력을 실제로 넣어 기대 행동이 나오는지 확인. 안 나오면 프롬프트 ③⑥ 수정 |
| **6 시연 로그** | `05_demo_log.md` | 40분 | 4단계에서 실제로 오간 대화를 정리. "첫 응답에서 확인할 것 3개"와 "안 나오면 되묻는 문장" |
| **7 마감** | `06_paste/` `module.md` `CHECK.md` | 40분 | `python3 tools/check_module.py <모듈ID>` 통과. 수동 항목 4개는 사람이 체크 |

4단계가 이 절차의 요점입니다. **정답은 쓰는 것이 아니라 돌려서 받는 것**입니다. 그래야 사내강사가 같은 프롬프트·같은 파일로 같은 결과를 재현하고, 시연 로그가 실제 대화가 됩니다(handoff_review F4).

## 6. 모듈 간 인터페이스 — 단독 실행이 기본, 체인은 선택

각 모듈은 `01_data/`에 **자기 시작 입력을 다 갖고** 있습니다. 앞 모듈 결과는 있으면 쓰고, 없어도 됩니다.

```
                      chain.out                     chain.in
A_sensing_b2b     ──▶ opportunity_list.csv ───┐
B_sensing_partner ──▶ opportunity_list.csv ───┼──▶ D_analysis (target_account.md 대신 사용 가능)
                                              │
D_analysis        ──▶ recommended_models.csv ─┴──▶ C_proposal (후보 모델 힌트로 사용 가능)
```

인계 파일의 컬럼은 두 개뿐이고 고정입니다.

| 파일 | 컬럼 | 만드는 모듈 | 받는 모듈 |
|---|---|---|---|
| `opportunity_list.csv` | `[수요처명] [버티컬] [프로젝트/용도] [근거]` | A, B | D |
| `recommended_models.csv` | `[순위] [모델명] [제품군] [근거]` | D | C |

수업 순서(② A/B → ③ C → ④ D)와 데이터 흐름(A/B → D → C)이 다르지만 문제가 없습니다. C는 자기 `customer_request.md`로 시작하고, D는 자기 `target_account.md`로 시작합니다. 체인은 "내 업무로 전환" 단계에서 "실제로는 ②의 결과가 ④의 입력이 됩니다"를 보여줄 때만 씁니다.

## 7. 삼성 양식 4개 → 요구조건서 4장

상세는 각 모듈 폴더의 `00_requirement.md`. 여기서는 모듈을 결정하는 값만 모았습니다. **모델명·회사명·수치는 전부 가상입니다.**

| 삼성 양식 | 3 | 2 | 1-1 | 1-2 |
| 케이스 | 버티컬 추천 | 요구조건 제안 | **상장 건설사 개척** | **권역 작은 시설** |
| 에이전트 수 | **1** | **1** | **1** | **1** |

## 8. 수업과 슬라이드에 꽂히는 방식

### 모듈 1개 = 2시간 = 에이전트 1개

**에이전트는 총 4개입니다.** 모듈당 하나이고, 2시간에 하나를 끝까지 만듭니다.
모듈 안에 단계가 여럿이어도(A·B·C는 셋) 에이전트는 하나입니다. 단계 사이에 🔒이 없기 때문입니다 (`common/task_decomposition.md` 4장).

본 과정 6시간은 이 중 셋(A 또는 B → C → D), 양성과정 2일은 넷 전부입니다.

### 2시간 표준 큐시트

| 구간 | 분 | 하는 것 | 쓰는 파일 |
|---|---|---|---|
| 프로세스·IPO | 20 | 이 일의 As-Is 프로세스와 단계별 IPO, 꼬리표, 묶음 | `module.md` 1절 분해표 |
| 시연 | 15 | 강사가 에이전트를 만들어 끝까지 한 번 | `05_demo_log.md` |
| 실습 1 | 30 | 에이전트 만들기 · 지침 붙여넣기 · 참조 파일 · **단계 1** 정상 테스트 | `02_prompt/` `01_data/` `test_normal.md` |
| 실습 2 | 25 | **단계 2·3** 진행, 결과 저장 | `02_prompt/` `web_environment.md` 3장 |
| 실습 3 | 15 | 경계·실패 테스트 + 5분 검수 | `test_boundary.md` `test_failure.md` `review_criteria.md` |
| 전환 | 10 | 스킬로 뗄 것 고르기 + 내 업무 표 | `agent_and_skill_split.md` · 워크북 부록 |
| 버퍼 | 5 | 못 따라온 참가자 `04_answer/`로 진입 | `04_answer/` |

**D는 단계가 하나라 실습 2가 짧습니다.** 남는 15분은 검수와 전환에 씁니다. 그래서 D를 첫 모듈로 놓습니다.

**모듈 1개 = 본 과정 2h 블록 1개.** `instructor_guide.md` 큐시트의 자리에 모듈 파일이 들어갑니다.

| 큐시트 구간 | 모듈에서 쓰는 파일 |
|---|---|
| 강의 (업무 상황·입력·출력) | `module.md` + `00_requirement.md` 본문 |
| 시연 15분 | `05_demo_log.md` 그대로 |
| 실습 1 — 프롬프트 붙여넣기·정상 테스트 | `02_prompt/` + `01_data/` + `03_tests/test_normal.md` |
| 실습 2 — 경계·실패·검수 | `03_tests/test_boundary.md` `test_failure.md` + `common/review_criteria.md` |
| 못 따라온 참가자 | `04_answer/` 정답 파일로 다음 단계 진입 |
| 내 업무로 전환 | `00_requirement.md` frontmatter를 빈칸으로 만든 워크북 표 |

슬라이드의 **[팀별] 9장은 `module.md`의 9개 절과 1:1**입니다. Claude Design에는 모듈 카드 4장을 첨부하면 되고, 팀별 분기는 A/B 모듈 카드의 차이로 자동 결정됩니다.

양성과정 2일(9/16~17)은 네 모듈을 다 돌립니다. 1일차 D·C(공통), 2일차 A·B(팀별). 사내강사가 D를 운영해 보면 나머지는 파일 위치가 같아서 학습 비용이 줄어듭니다.
